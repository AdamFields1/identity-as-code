# ADR 0021: Entra enterprise applications as a catalog shape

Status: accepted
Date: 2026-09-20

## Context

ADR 0020 gave the Okta tree an application catalog: SAML and OIDC apps as
entries in a values-only fragment, with the guardrails in the modules and
the cross-map checks in the stack. Entra has the same need. An enterprise
application over SAML is either a gallery application (a template Microsoft
publishes for a vendor, carrying the vendor's app roles and, where the
vendor has one, a provisioning connector) or a custom application (a service
provider with no gallery entry, whose entity id, assertion consumer service
URL, claims, and app roles the tenant declares itself). Onboarding one is
the same everyday work the Okta catalog absorbed, and until this change the
Entra tree had a shape for exactly one of them: `modules/entra/aws-identity-center-app`
instantiates a gallery template, adopts the service principal the
instantiation creates in SAML mode, has Entra generate a signing
certificate, assigns groups by display name to the app role the template
publishes, and configures SCIM from variables the cell never mentions. That
module was written for one vendor, and its shape (the
`AWS-<PARTITION>-<accountId>-<PermissionSetName>` group convention and the
partition token) is that vendor's.

Hand-onboarded enterprise applications fail in the same few ways, and each
is a setting nobody meant to choose. The signing certificate is created in
the portal with a three-year expiry and no notification address, or with
the address of an engineer who has since left, so the first sign of its
expiry is the outage. Assignment is not required, so every user in the
tenant can open the application, and the vendor's licence count or the
application's own admin page is the only audit. The claims are typed as
JSON into a claims mapping policy through Graph Explorer and pasted into a
wiki, so the next person to change one attribute edits a document nobody
reviews and nothing validates. The group claim is set to every group the
user belongs to, so the vendor receives the directory's group names on
every assertion. The SCIM token travels in a ticket. The vendor's copy of
the metadata is a screenshot rather than a URL, so a certificate rotation
is a support call. None of these is a design decision; each is a default
that survived because nothing refused it.

## Decision

`stacks/entra-enterprise-apps` is a catalog in shape and a platform stack in
placement, as `stacks/okta-applications` is (ADR 0020): one cell per tenant
that onboards applications, in this repository corp only, written as a
fragment cell (`tenants/azure/corp/entra-enterprise-apps/saml-apps.hcl`),
and one module, `modules/entra/saml-enterprise-app`, which generalises the
Identity Center module into a map of SAML service providers keyed by logical
name, gallery or custom by one field. The Identity Center module stays as it
is, because its group convention is the AWS assignment (ADR 0008), and its
README points at the general module as the pattern's home.

**The shape.** Per application, a cell says its display name; the gallery
template's display name, or nothing for a custom application; the entity id
(`identifier_uris`, a URI or the bare identifier a gallery application such
as Google Workspace requires); the assertion consumer service URLs
(`reply_urls`); the sign-on URL; an optional logout URL and relay state; the
addresses mailed before the signing certificate expires; the certificate's
display name and an optional end date; how the subject is named (`name_id`,
a source and a format from allowlists); the claims, each a name and a source
from an allowlist; the app roles and the groups assigned through them; an
enabled flag; and, for a token-based connector, the provisioning template and
endpoint. Everything else is refused, not defaulted, so a mistake is visible
in review: a non-https or wildcard endpoint, an empty reply list, no
notification address, an unknown NameID source or format, an unknown claim
source, a claim or app role named twice, a display name used twice, a
provisioning token or endpoint with no template.

**What is fixed.** Assignment is required and `saml` is the sign-on mode;
neither has an input. The signing key is generated by Entra and never leaves
the tenant. The endpoints are https with a host and no wildcard. The group
claim, when an application asks for one, is limited to the groups assigned
to the application. Owners, tags, branding, optional claims, and the group
membership claim setting are set at creation and then ignored, the same
inventory-and-guardrail contract as `modules/entra/app-registration` (ADR
0006): Terraform is the inventory and the guardrail, not the sole editor,
and the entity id, reply and logout URLs, certificate, claims policy, and
assignments are enforced on every apply because they are where the
assertion goes.

**Claims are typed values rendered by the module.** `name_id` and `claims`
are names and sources. The module renders one `azuread_claims_mapping_policy`
per application with `jsonencode` and binds it to the service principal, so
the JSON exists only in the plan and a cell never contains a policy document
(ADR 0002). Two facts about Entra shape the rule. A claims mapping policy has
no element for the NameID format, and Entra honours the `NameIDPolicy` the
service provider sends, so `name_id.format` is validated and handed to the
vendor as the URN to request, not enforced. And `groups` is not a claims
mapping source, so a claim with that source sets the application's group
membership claim to the assigned groups and adds the `groups` optional claim
carrying display names, which is why it must be named `groups`.

**Groups are names.** Every distinct group name across every application is
looked up once with a data source. The groups are created in
`stacks/entra-app-registrations` or provisioned outside this repository;
nothing here creates them, and the cell carries no `dependencies` block
because no cell on the release train has to precede it.

**App roles are resolved, never typed, and the two kinds differ.** A gallery
application's roles are the template's: the module reads them from the
instantiated service principal and picks the one enabled user-assignable
role whose display name matches, and a precondition fails naming the missing
role and listing what the template publishes. Those roles are computed until
the application exists, so on the first run of a new gallery application the
check is deferred to apply, where the application, service principal, and
certificate are created and the assignment fails with the message; on every
later plan the roles are known and the check runs at plan. A custom
application declares its own roles from the keys of `app_roles_to_groups`,
with ids derived from the application key and the role name, so its check
is a validation and its role set is enforced on every apply. This is why the
module holds two `azuread_application` resources: `ignore_changes` is
static, a gallery application must ignore `app_role` (the provider reads the
template's roles back on every refresh and would otherwise plan to remove
them), and a custom application must enforce it.

**The certificate expiry mail is part of the shape.** At least one
notification address is required, because the expiry of a signing
certificate is the failure the portal makes easiest to set up and hardest to
see coming. Rotation is a new certificate here and a metadata re-import on
the vendor's side.

**Provisioning is optional, and the Google consent step is stated.** A
connector that takes a SCIM endpoint and a bearer token is the Identity
Center pattern: the cell states the synchronization template and the
endpoint, and the token arrives through `TF_VAR_provisioning_secret_tokens`,
a sensitive map keyed by application that the stack passes to the module's
own sensitive input beside the map, never through a cell and never inside
the map. Google Workspace's connector is
authorised by an administrator consenting in a Google dialog the portal
opens, which Terraform cannot perform, so the cell leaves `provisioning`
unset and the stack README shows the one console step. Nothing about that
step is in state and the stack never reports drift on it, which is the
honest shape: a fake `provisioning` block would look managed and be
nothing.

**The custom template is resolved by its published id.** The brief for this
change resolved the non-gallery template by display name, as the Identity
Center module resolves its gallery entry; no public page states that
template's display name, so the module holds the id Microsoft publishes for
it (the same constant in every tenant of the global cloud, with the US
Government and China ids one variable away) and the data source confirms it
exists at plan. The placeholders lint knows the id through
`tools/repo_lint/microsoft_builtin_ids.txt`, where every published Microsoft
constant the tree uses is listed.

**The stack checks across the map at plan.** No two applications share a
display name, compared without case, because Entra's duplicate check is
case insensitive; no reply URL appears on two applications, because an ACS
URL belongs to one service provider; no entity id appears on two, because
Entra requires identifier URIs to be unique in the tenant; and every
provisioning token names an application of the cell that provisions.

**Parity with the Okta catalog.** The corp cell onboards the same fictional
payroll vendor `tenants/okta/prod/okta-applications/saml-apps.hcl` onboards:
the same entity id, ACS URL, subject, and group names, so the vendor is
configured once and trusts either identity provider; the attributes are each
provider's rendering of the vendor's guide (Okta sends `name` from
`displayName`, Entra sends `firstName` and `lastName`). That is the
promise the two catalogs make together: one shape per protocol, the same
values from either side, and the guardrails in the modules rather than in
whoever clicked last.

**The vendor gets outputs, not a console session.** After apply,
`vendor_onboarding` holds, per application, the issuer, the login and
logout URLs, the metadata URL (which carries the public certificate), the
certificate thumbprint, and the NameID format to request. The tenant's
endpoints and each metadata URL are built from the provider's tenant id and
never typed, and none of it is secret.

## Consequences

- **A missing group fails the plan.** A pull request that onboards an
  application for a group that does not exist yet plans red with the
  group's name. The practice is to create the group first, in the app
  registrations cell or wherever groups are provisioned, and open the
  pull request next; where the two must travel together, say so in the
  description. An empty assignment would be worse: an application that
  looks onboarded and that nobody can open.
- **A gallery template's app roles are the template's.** A cell names a
  role the template publishes, usually `User`, and cannot add one. The
  first run of a new gallery application creates the application and fails
  the assignment if the name is wrong, with the published roles in the
  message, and the corrected name completes on the next run; every later
  plan checks at plan. A vendor whose gallery entry publishes no
  user-assignable role is outside the shape today.
- **The metadata URL and the endpoints are outputs.** A certificate
  rotation is a new certificate in the cell and a metadata re-import on the
  vendor's side from the same URL, not a screenshot exchanged over email.
  The thumbprint in the output is what to compare against the vendor's
  view after the import.
- **The token lives beside the map, not in it.** The stack harness found
  that a token merged into the module's `saml_apps` map could not plan: the
  stack takes the token from a sensitive variable, which is the only
  correct source, and Terraform refuses a `for_each` over a value derived
  from a sensitive one, so a synchronization secret that iterated a
  credential map built from the token failed on every plan that set one.
  The shape was changed rather than the sensitivity stripped: the token is
  its own sensitive input on the module and on the stack
  (`provisioning_secret_tokens`, keyed by application), the map's
  `provisioning` is the template and the endpoint only, the secret iterates
  the applications whose `provisioning` sets an endpoint or whose key has a
  token, and the one `nonsensitive()` in the module is on that variable's
  keys, which are application names and say nothing about the token. The
  corp cell sets no token (Google Workspace is authorised in the console and
  the payroll vendor has no connector) and is unaffected either way.
- **The release train gained a job pair, and the pull request workflow
  gained nothing.** `azure-release.yml` plans and applies the corp cell after
  `apply-corp-roles`, beside the governance chain rather than inside it,
  because nothing the train applies has to precede it, and the subsidiary
  gate waits for its apply like any other corp cell. `azure-pr-validation.yml`
  discovers cells generically, so the new cell is planned on a pull request
  that touches it with no workflow edit.
- **OIDC enterprise applications, password-based and linked sign-on, and
  the connectors' OAuth authorisations stay out of scope.** OIDC
  applications are app registrations and already have a shape
  (`modules/entra/app-registration`); the other two sign-on modes have no
  shape here rather than a half-built one; and an OAuth consent is a person
  in a dialog, stated as such.
- **What a first apply should confirm.** That the gallery template is found
  under the display name the cell gives and publishes a `User` role, since
  the first run checks it at apply; that the provider accepts the bare host
  identifier the Google Workspace gallery entry requires as an identifier
  URI, since a host is not a URI and the tenant's verified-domain rule may
  be applied to it; that the second plan of a gallery application shows no
  diff on its app roles, and, the same question asked of the older module,
  that the second plan of an Identity Center application (which does not
  ignore `app_role`) does not propose removing the template's roles; that
  the claims mapping policy issues the mapped claims with the service
  principal's own signing key and without `acceptMappedClaims`; that the
  groups claim carries display names rather than object ids; that the
  certificate thumbprint in `vendor_onboarding` is the one the vendor's
  metadata import shows; that the expiry notification reaches the address
  the cell names; and that the group names in the cell have been created
  before the first plan, since the plan and not the apply is what fails
  otherwise.
